# [TASK-001] Implement Data Quality Checks

**Status:** `Open`  
**Priority:** `High`

## 1. Project Owner's Perspective

### Goal
To build trust and reliability into our data pipelines by systematically validating all incoming data. We must prevent "garbage in, garbage out" scenarios to ensure the accuracy of our ML models and analytics.

### User Story
"As a Data Platform Owner, I want all data entering our feature engineering pipelines to be automatically validated against a predefined schema, so that we can guarantee data integrity, prevent unexpected errors, and maintain the accuracy of our fraud detection models."

### Value Proposition
- **Increased Reliability:** Prevents pipeline failures caused by unexpected data formats or types.
- **Improved Model Accuracy:** Ensures models are trained and scored on high-quality, valid data.
- **Faster Debugging:** Immediately pinpoints data issues at the source, rather than deep within a complex pipeline.
- **Enhanced Trust:** Builds confidence in the data and the insights generated by the DAFU platform.

### Acceptance Criteria
- All data loaded for `fraud_detection` and `customer_analytics` is validated before processing.
- The system must check for correct data types, required columns, and valid value ranges.
- If validation fails, the pipeline should stop and log a clear, actionable error message detailing the validation failure.
- The validation logic must be testable and have its own unit tests.

---

## 2. Technical Analysis & Implementation Plan

### Current State
Currently, the data loading process in our preprocessing scripts reads data directly into a pandas DataFrame. While some pandas-native type handling occurs, there is no explicit, structured validation layer. An unexpected `null` value or a string in a numeric column could cause silent errors or downstream failures.

### Proposed Solution
We will integrate **Pandera**, a powerful and expressive data validation library for pandas DataFrames. We will define a strict `SchemaModel` for each of our primary input datasets. This schema will be used to validate the DataFrame immediately after it is loaded.

### Step-by-Step Implementation
1.  **Add Dependency:** Add `pandera` to the main `requirements.txt` file.
2.  **Create Validation Module:** Create a new file, e.g., `core/features/validation.py`, to store the reusable Pandera schemas.
3.  **Define `FraudDetectionSchema`:** In `validation.py`, define a Pandera `SchemaModel` for the fraud detection input data. This schema should specify:
    - All required columns (`transaction_id`, `user_id`, `amount`, etc.).
    - The expected `dtype` for each column (e.g., `pa.Float`, `pa.String`, `pa.DateTime`).
    - Constraints using `pa.Check` (e.g., `amount` must be greater than or equal to 0).
    - Nullability checks (e.g., `user_id` cannot be null).
4.  **Define `CustomerAnalyticsSchema`:** Similarly, define a Pandera `SchemaModel` for the customer analytics input data, enforcing its specific column and type requirements.
5.  **Integrate into Pipelines:**
    - In `core/features/fraud_detection/src/feature_engineering/temporal_features.py` (or wherever data is first loaded), import the `FraudDetectionSchema`.
    - Immediately after loading the data into a DataFrame, call `FraudDetectionSchema.validate(df, lazy=True)`.
    - Wrap the validation call in a `try...except` block to catch `pandera.errors.SchemaErrors` and log a descriptive error message before exiting.
    - Repeat this integration for the customer analytics pipeline.
6.  **Write Unit Tests:** Create a new test file, `core/features/test_validation.py`.
    - Write a test that passes a valid DataFrame to the schema.
    - Write tests that pass invalid DataFrames (e.g., with missing columns, wrong dtypes, out-of-range values) and assert that the correct `SchemaErrors` are raised.

### Key Files & Directories to Modify
- `/requirements.txt` (Add `pandera`)
- `/core/features/validation.py` (New file)
- `/core/features/fraud_detection/src/feature_engineering/temporal_features.py` (Or other data loading script)
- `/core/features/customer_analytics/preprocessing.py` (Or other data loading script)
- `/core/features/test_validation.py` (New file)

### Testing Strategy
- **Unit Tests:** Test the Pandera schemas directly with sample valid and invalid DataFrames.
- **Integration Tests:** Modify existing pipeline tests to ensure that a pipeline run with invalid source data fails at the validation step with a clear error.
- **Manual Verification:** Run a pipeline manually, point it to a deliberately corrupted CSV file, and confirm that the process halts with the expected validation error message.

## 2.1. Deep Dive: Engineering Perspective

### Schema Management and Reusability
To avoid code duplication and make schemas more maintainable, we should implement a simple "Schema Registry" pattern within our `validation.py` module. This can be a dictionary that maps dataset names or pipeline stages to their corresponding Pandera `SchemaModel`.

```python
# core/features/validation.py

import pandera as pa

class FraudDetectionSchema(pa.SchemaModel):
    # ... schema definition ...

class CustomerAnalyticsSchema(pa.SchemaModel):
    # ... schema definition ...

SCHEMA_REGISTRY = {
    "fraud_detection_raw": FraudDetectionSchema,
    "customer_analytics_raw": CustomerAnalyticsSchema,
}

def get_validator(schema_name: str):
    """Retrieves a configured validator from the registry."""
    schema = SCHEMA_REGISTRY.get(schema_name)
    if not schema:
        raise ValueError(f"Schema '{schema_name}' not found in registry.")
    return schema
```
This approach allows our pipelines to request a validator by name, centralizing schema management.

### Performance Considerations
Data validation adds overhead. For very large datasets (10M+ rows), validating the entire DataFrame at once can consume significant memory and time. Pandera's `lazy=True` parameter is critical here, as it collects all validation errors before raising an exception, but the validation itself is still eager.

**Strategy for Large Data:** For batch jobs running on extremely large files, validation should be performed on a *sample* of the data first (e.g., the first 10,000 rows) for a quick check. For streaming data, validation should occur on a micro-batch basis.

### Advanced Validation and Error Handling
- **Custom Checks:** We should leverage `pandera.Check` to write complex, business-specific validation rules. For example, a cross-column check to ensure that `transaction_amount` is zero if `transaction_type` is 'account_verification'.
- **Structured Logging for Failures:** When a `SchemaError` is caught, the error logging should be structured (e.g., JSON format). This allows us to easily parse validation failures in our logging platform (like Splunk or an ELK stack) and create automated alerts. The log should include the schema name, the error type, and a sample of the failing data from the `SchemaError` object.
- **Data Quality Alerting:** In a production setting, a validation failure should trigger an alert. This could be a message to a Slack channel or an event sent to a monitoring system like Prometheus (which can be scraped to trigger alerts in Alertmanager). This moves us from passive failure to proactive monitoring.
